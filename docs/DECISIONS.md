# 기술 결정 기록

## D1. 프로젝트 Python 3.12 + uv 가상환경 (2026-10-17)
- 시스템에는 Anaconda Python 3.11만 있음. 요구사항(3.12)과 "기존 환경 수정 금지"를 지키기 위해 uv가 관리하는 3.12.9로 `.venv`를 만든다.

## D2. Joy-Con 입력: joycon-python + hidapi로 시작 (2026-10-17, Phase 1 검증 대기)
- 근거: Python 학습 코드와 같은 프로세스에서 쓸 수 있고, 의존성이 작으며(hidapi는 cp312 Windows 휠 존재), L/R을 PID(057E:2006 / 057E:2007)로 구분한다.
- 소스 확인으로 알게 된 제약과 대응 (`src/teachabot/input/joycon_device.py`):
  - get_status()는 리포트당 IMU 샘플 3개 중 첫 번째만 줌 → 3개 모두 직접 읽음.
  - 생성자가 타임아웃 없는 블로킹 read를 함 → 별도 스레드 + 타임아웃으로 감쌈.
  - 리더 스레드 종료/close API가 없음 → 재연결 시 세대(generation) 번호로 옛 핸들의 샘플을 버림.
  - 스틱 보정값을 쓰지 않음(원시 12-bit) → Phase 2에서 중립 보정·Dead Zone 구현.
  - serial을 무시하고 VID/PID로 첫 장치를 염 → L 1개 + R 1개 전제.
- **확정 (2026-10-17 Phase 1 실기 검증)**: Windows 11 + Realtek BT 5.0에서 L/R 동시 66.7Hz 리포트(IMU 200Hz), 버튼·스틱·IMU 전부 정상, 연결 해제·재연결 동작 확인. 라이브러리 교체 불필요.
- 대안(실패 시) — 현재 불필요: hidapi로 직접 프로토콜 구현(dekuNukem 문서), everything-imu(Rust, MIT, Joy-Con 200Hz 검증됨) 브리지, Unity + UnityJoyCon.

## D3. 입력 표준 형식과 신호 처리 (2026-10-17, Phase 2)
- `InputFrame` schema v1: 스틱 [-1,1] (+x 오른쪽, +y 위), 손별 고정 버튼 집합(grip=ZL/ZR), accel[G]/gyro[dps]. 끊긴 손은 connected=False + 중립값을 스키마 수준에서 강제 → 게임은 별도 처리 없이 안전 정지.
- 스틱: 접속 시 정지 상태 20리포트 중앙값으로 중립 보정(실측 중립이 세션마다 수십~수백 단위 이동), 방향별 범위를 관측 최대치로 확장(상한 1700), 원형 Dead Zone 0.12(축별 Dead Zone은 대각선 방향을 왜곡).
- Debounce 12ms = 15ms 리포트 기준 2회 연속 일치. 지연 약 15ms 추가.
- 신호 처리는 poll()에서 리포트 타임스탬프 순으로 수행 → 게임 프레임레이트와 입력 샘플링 분리.
- 기록 형식: JSONL(헤더 + 프레임), schema 이름·버전 검사. Replay는 학습 결과가 아님을 모듈 문서에 명시.

## D4. R→L IMU 축 매핑 보류 (2026-10-17)
- 손으로 붙여 기울이는 방식은 실측에서 신뢰할 수 없었음(동시 회전 구간 짧음, R 가속도 스케일 +9%). 상관계수 기반 추정은 결합된 축(x·z)에 속아 잘못된 확신을 냄 → Kabsch(최적 회전) 기반으로 교체하고 잔차·부호행렬 조건으로 검증.
- IMU는 MVP 조작에 쓰지 않으므로 축 통일은 필요할 때 정지 자세 방식으로 측정. 그 전까지 R IMU는 센서 좌표계, `meta.imu_frame_verified=false`.

## D5. 3D 엔진: Ursina 8.3.0 (2026-10-17, 사용자 결정)
- 근거(실측): 한글 경로에서 PNG·OBJ 로드와 Panda3D 로더(.bam 쓰기·읽기) 정상, 맑은 고딕 한글 HUD 정상(시스템 폰트를 그 자리에서 사용, 저장소에 복사하지 않음), Joy-Con 매 프레임 폴링 포함 60.0fps(p99 18ms, 폴링 0.05ms/프레임), 리포트 수신 ~65Hz 유지. 입력·학습 코드를 같은 Python 프로세스에서 재사용. Unity는 미설치.
- vsync를 꺼도 60fps 상한(드라이버/OS 동기화로 추정). 목표가 60fps라 문제 없음.
- 주의: `Entity.default_shader = None`은 전부 검게 렌더링됨 → `lit_with_shadows_shader` 사용, 바닥 표시는 `unlit_shader`.

## D6. 시뮬레이션과 렌더링 분리 (2026-10-17)
- `simulation/environment.py`는 순수 Python(고정 1/60초 스텝). Ursina(`ui/scene.py`)는 상태를 그리기만 함 → 에셋 교체·엔진 교체가 학습 코드에 영향 없음, AI 평가를 창 없이 빠르게 실행 가능.
- 파지는 교육용 추상화: 열림→닫힘 순간 반경 0.05 안의 자유 큐브를 부착, 열면 그 자리에 내려놓음. 닫은 채 큐브 위로 가도 집히지 않음. 연결이 끊긴 손은 grip=False가 되어 들고 있던 큐브를 놓음.

## D7. 모션 조작(기울이기/가리키기) — 사용자 요청 (2026-10-17)
- IMU는 위치 센서가 아니므로 "가상 스틱"으로 변환해 게임 코드는 그대로 둠(`input/motion.py`, `MotionControlProvider`).
  - 기울이기: 가속도 저역통과(3Hz) 중력 방향, 1G에서 크게 벗어난 샘플은 가중치 1/10(손 흔들기 억제), 보정 기울기의 80%에서 최대 속도, 원형 Dead Zone 0.15. 드리프트 없음.
  - 가리키기: 바이어스 제거된 각속도를 보정으로 얻은 yaw/pitch 축에 투영, 8dps Dead Zone, 90dps에서 최대 속도.
- 손별 보정(가만히 → 앞으로 기울이기 → 오른쪽 기울이기 → 오른쪽 가리키기)으로 모든 축을 그 조이콘의 센서 좌표계에서 학습. L/R 칩 방향이나 가속도·자이로 부호 관례를 가정하지 않음.
- 실측으로 이 선택이 맞았음을 확인: 같은 자세로 쥐었을 때 L/R 가속도는 세 축 부호가 모두 반대(반사 관계), 자이로는 또 다른 관계. D4에서 가정한 "고유 회전(det=+1)" 관계는 틀렸음 → R→L 공통 좌표계가 필요해지면 반사를 허용해 다시 측정해야 함.

## D8. 이동 방식: 웹캠 손 위치(메인) + 조이콘 자세·집기, A′ 체험 모드 (2026-10-18, 사용자 결정)
- 근거: IMU 스트로크 실측(32회)에서 방향 94%·거리 5cm 이내 22% → IMU로 이동량 불가. 업계 조사(Wii IR, Quest/PS Move 카메라, 스위치 2 광학 센서, 조이콘 로봇 오픈소스는 스틱)도 "IMU = 자세, 이동 = 절대 기준".
- 시범용 메인(B): 웹캠으로 손의 절대 위치 → 집게 X/Z, 조이콘 기울기 → 손목 자세·높이, ZL/ZR → 집기.
- 체험 모드(A′): 닌텐도 방식 — 손을 휙 옮긴 방향을 인식해 집게를 한 칸 이동 (방향 인식 94% 실측 활용).
- 다음 확인: 웹캠 배치(정면 vs 비스듬히 위)별 검출률·떨림·위치 오차 실측.

## D9. 이동은 스틱, 조이콘 자세는 손목 회전·기울기 — 모션 이동은 보류 (2026-10-19, 사용자 결정)
- 사용자: "모션기반 이동 방식은 일단 나중에 진행할 수 있게 추가 보정은 두고, 스위치 컨트롤러로 회전·기울기 쓰고, 스틱으로 이동을 하던 방법을 다시 사용하자. 나중에 바꿔가면서 설정할 수 있게."
- 기본 조작: 스틱 → 집게 이동, 조이콘 자세(IMU) → 집게 손목 회전·기울기, ZL/ZR → 집기.
- 보류(삭제하지 않음): D8의 웹캠 손 위치 이동(B), A′ 동작 방향 한 칸 이동, 기존 기울이기/가리키기 이동 모드. 측정 도구(`record_webcam_hands.py`, `--distance-sim` 포함)와 분석 스크립트는 그대로 둠. 거리 모의 녹화(`webcam_dist_front_20261018_025300.jsonl`, 32KB)는 중간에 멈춘 것으로 보이며 분석하지 않음.
- 설정으로 전환: 이동 소스(stick / tilt / point / webcam / stroke)와 자세 소스(imu / off)를 설정 파일과 실행 옵션으로 고를 수 있게 함. 게임·학습 코드는 이동·자세 "명령"만 받으므로 소스 교체가 학습 데이터 형식에 영향 없게 유지.
- 손목 자유도(회전·기울기)는 시뮬레이션 쪽 변경이 필요하므로 3D 환경 선택(D10) 후 구현.

## D10. 3D 환경: MuJoCo 3.16 + Menagerie ALOHA 2 (2026-10-19, 사용자 결정)
- 근거: 실제 양팔 모방학습 연구 로봇(ACT·LeRobot 플랫폼) → "학생이 가르치면 AI가 따라 한다"를 연구 장비로 보여 줌. 강화학습 단독 vs 모방학습 비교 시연을 같은 환경에서 할 수 있음. 무료(Apache-2.0 / 모델 BSD-3), Windows cp312 휠, 렌더 1280×720 11ms.
- 비교한 대안: Ursina + 에셋(위험 최소, 화질 한계), Unity/Godot 렌더러(2~3일, 2프로세스), Isaac Sim(설치·학습 비용 큼). 조사: `잡동사니/blog_materials/13_*.md`, 갤러리 `examples/asset_gallery.html`.
- 구조: `teachabot.aloha` (scene / env / teleop) + `teachabot.aloha_app`. 사람과 AI는 같은 `ArmCommand`(이동 x·y, 높이 속도, 손목 기울기·회전, 집기)를 냄 → mink IK(daqp) → 관절 위치 제어. 50Hz 제어, 물리 2ms. 중력 보상은 mink 예제와 같은 방식. 집기는 순수 접촉 물리(부착 보조 없음).
- 한글 경로: MuJoCo도 "잡동사니" 경로의 파일을 못 엶 → XML·메시를 바이트로 메모리에 올리고 `<include>`는 직접 펼쳐서 `MjSpec.from_string(assets=...)`.
- S1 제약(실측): 두 큐브가 가운데에 가까우면 두 집게 몸체가 충돌(사이트 간격 ~0.19m), 받침대에 너무 가까운 큐브는 아래 향한 자세로 도달 불가 → 큐브 생성 x ∈ ±[0.13, 0.26], y ∈ [−0.16, 0.04], 손별 작업 범위 x: 왼손 ≤ −0.10, 오른손 ≥ 0.10.
- 높이 조작: L/R 누르고 있기 = 내리기, 떼면 운반 높이로 복귀(버튼 1개, 학생용). 손목: 조이콘 중력 방향(저역통과) → 앞 기울기 = 집게 기울기(±45°), 옆 기울기 = 집게 회전(±90°), Dead zone 4°. A 버튼으로 시작할 때 쥔 자세가 손목 기준.
- 모델 파일은 git 미추적: `scripts/download_aloha.py`(고정 커밋 71f066a + sha256 검증).

## D11. 강화학습 기준선: PPO, 같은 관측·행동, 희소/촘촘한 보상 두 가지 (2026-10-19)
- 목적: "강화학습만으로는 잘 안 된다"를 **연출 없이 실측**으로 보여 주기. 결과가 어떻든 그대로 쓴다(촘촘한 보상 쪽이 결국 성공해도 그것이 결과).
- 공정성: 사람·모방학습과 **같은 관측(v2, 40차원)과 같은 명령 형식**. 강화학습에 유리하게 결정 주기는 10Hz(제어 5스텝 반복), 학습 배치는 무작위 배치(seed < 1,000,000), 평가는 처음 보는 배치(seed ≥ 1,000,000) 10판, 결정적 행동.
- 보상: 희소 = 각 큐브가 처음 자기 상자에 들어갈 때 +1(판당 최대 2). 촘촘한 보상 = 손별 단계 보상(다가가기 → 잡기 → 들기 → 상자 쪽 이동 → 상자 안 3.5) × 0.1 + 성공 20. "사람이 보상을 잘게 설계해 주는" 변형.
- 구현: stable-baselines3 2.9.0 PPO, MLP 256×256, n_steps 1024 × 8 환경(SubprocVecEnv), batch 4096, 10 epoch, lr 3e-4, γ 0.99, VecNormalize(관측; 보상 정규화는 촘촘한 보상만). 100만 스텝마다 평가 + 체크포인트(그 시점 정책의 실제 행동을 보여 줄 수 있음). `progress.csv`에 연습 시간(시뮬레이션 시간) 기록.
- 처리량(실측): 두 실행 동시에 각 ~430스텝/초 ≈ 실제 1시간에 연습 ~45시간.
- 관측 v1(30차원)로 시작한 첫 실행은 30분 만에 중단·보관(`data/rl_runs/_discarded_obs_v1`): 모방학습 쪽에서 상대 좌표가 필요하다는 것이 밝혀져 관측을 바꿨고, 비교를 공정하게 하려면 강화학습도 같은 관측이어야 하므로.

## D12. 모방학습(BC): 상태 기반 MLP, 상대 좌표 관측, 병렬 자동 평가 (2026-10-19)
- 시범: 앱 `--record 세션코드`가 판마다 (관측, 사람 명령) 쌍을 50Hz로 `data/demos/s1/*.npz`에 저장. 이름 없이 익명 코드만. 시작 버튼 후 아무것도 안 한 앞부분은 학습에서 제외.
- 정책: MLP 3층(256), 연속 명령 10개(tanh, MSE) + 집기 2개(BCE). AdamW, 4000 반복(약 7~13초, CPU). 학습한 망은 numpy로 내보내 평가·앱에서 torch 없이 실행.
- **측정으로 고친 것 두 가지** (테스트 전용 스크립트 시범으로 파이프라인 검증 중 발견):
  1. 시범에서 항상 0이던 값(손목 각도)을 표준편차 0.001로 나눠, 실행 중 조금만 움직여도 입력이 수십 배로 튐 → 정책이 학습 데이터에 없던 출력(기울기 최대) → 표준편차 하한 0.05.
  2. 정책이 큐브를 약 1cm 빗나가 빈손으로 들어 올림 → 관측에 "큐브 − 집게 목표", "상자 − 큐브" 상대 벡터 추가(관측 v2). 스크립트 시범 20개 기준 성공 0% → 30%.
- 스크립트 시범 결과는 **파이프라인 검증용**이며 학생 데이터나 시연 결과로 쓰지 않는다.
- 평가: 처음 보는 배치 20판을 10개 프로세스로 병렬 실행(약 15초). 판마다 실제 물리 속 폐루프 실행.

## D13. 모방학습 v2: 손별 공유망(좌우 대칭) + 기다림 구간 잘라내기 + 앞을 보는 정답 (2026-10-19, 사람 시범으로 실측)
- 계기: 사용자 시범 11판(성공 10, 한 판 10~23초)으로 D12(로봇 전체 MLP)를 학습 → 처음 보는 배치 20판 **성공 0%, 상자에 넣은 큐브 0**. 정책이 반대쪽 구석으로 가서 멈춤.
- 측정한 원인: 사람은 스틱을 짧게 툭툭 치고 한 손씩 움직임 → 한 손 스틱이 움직이는 프레임 11%, 두 손 동시 5%. 데이터 대부분이 "기다림"이고, 언제 기다릴지는 사람의 주의에 달려 있어 로봇이 볼 수 있는 상태로는 정해지지 않음. 손목 출력은 되먹임으로 학습 범위 밖(31°)까지 커짐.
- 바꾼 것(`learning/bc_hand.py`, 기본 `train_bc.py --algo hand`):
  1. 손별 입력(자기 목표·집게·큐브·상자, 18차원, 손목 명령값 제외)으로 하나의 망을 두 손이 공유. 오른손은 x를 뒤집어 왼손 좌표로(데이터 2배).
  2. 손마다 "할 일이 남았는데 아무것도 안 한 프레임"을 시간축에서 잘라 냄 → 멈춤 직전 프레임 다음에 사람이 실제로 한 동작이 이어짐.
  3. 정답 = 다음 10개 (동작) 프레임의 평균 명령, 집기 정답 = 10프레임 뒤 상태.
- 실패에서 배운 순서(실측, 시범 10개, 평가 20판): 손별·대칭·평균 정답만 → 0% / 기다림 구간 전부 삭제 → 상자 위에서 놓지 않음(놓기 직전의 멈춤까지 지움) / 0.5초 이상 기다림만 삭제 → 큐브 위에서 내려가지 않음(같은 정지 상태에 "기다림"과 "내림" 정답이 섞여 평균 = 정지) / **시간 압축** → 10% (큐브 0.65개).
- 설정 선택은 **튜닝 전용 배치(seed 2,000,000~)**에서: 정답 길이 {5,10,20} × 집기 예측 {2,5,10} 중 10/10 (성공 25%, 큐브 1.05). 보고 숫자는 별도 평가 배치(seed 1,000,000~).
- **시범 수별 결과 (평가 배치 40판, 사용자 시범 s01)**: 1개 0%(큐브 0.03/판) · 2개 0%(0.05) · 3개 2%(0.25) · 5개 8%(0.53) · 10개 **25%(0.95)**. `data/policies/bc_curve_s01_20261019_192453.csv`

## D16. S2 양팔 트레이 들기 — 첫 구현과 남은 설계 질문 (2026-10-20 새벽)
- 구성: 트레이 30×16cm(테두리 1.2cm), 양 끝 손잡이 3×2.5×5cm(집게가 2.5cm 두께를 가로질러 잡음, 손잡이 중심 x=±13cm), 트레이 위 큐브 4cm(마찰 0.5), 목표 노란 칸 (0, 0.22). 조작은 S1과 같음(학생 두 명이 조이콘 하나씩).
- 판정: 성공 = 트레이가 내려놓인 상태(들림 <1cm, 기울기 <18°)로 중심이 목표 칸 안 + 큐브가 트레이 위. 실패 사유 cube_off / tray_fell / timeout(40초).
- S1 영향 없음: 환경에 확장 지점만 추가, 난수 순서 유지(seed 6개 배치 동일 확인 + 회귀 테스트). S2 시범은 task="s2"로 저장되어 S1 학습에 안 섞임.
- 시험(테스트 전용 스크립트, 사람 아님): 10/10 운반 성공, 약 3.3초. **오른팔을 1초 늦게 들어도(기울기 23°) 큐브가 안 떨어짐 → 지금은 쉬운 과제.** 공(반지름 2cm)+낮은 테두리(0.4cm)로 바꾸면, 늦게 드는 것과 무관하게 목적지에서 급정지할 때 공이 굴러 떨어짐(내려놓기 단계, 정지 0.2초 뒤).
- **사용자 결정 대기**: (A) 큐브+테두리 그대로(쉬움, 협동 연습용) / (B) 공+낮은 테두리(부드럽게 나르기가 핵심, 스틱 조작으로는 어려울 수 있음) / (C) 큐브 + 기울기 규칙(예: 20° 넘으면 실패, 들기 동기화가 핵심). 학습(BC)·견학 모드·강화학습 기준선은 사람 시범을 모은 뒤.

## D17. S2 = 공 + 0.6cm 테두리 (B안, 2026-10-20 사용자 결정) — 핵심은 "부드럽게 나르기"
- 사용자: "B로 가 보자." (D16의 A/B/C 중 공 + 낮은 테두리)
- 테두리 높이는 스크립트 시험(사람 아님, 두 팔 동시에 들기, 배치 10개)으로 정함: 0.4~0.5cm는 부드럽게 날라도 떨어짐, **0.6cm는 거칠게(최고 속도로 출발·정지) 0/10 · 부드럽게(5cm 가속, 8cm 감속) 10/10**, 0.7cm 거칠게 6/10, 0.8cm 이상은 안 떨어짐.
- 측정으로 알게 된 것: 한 팔을 0.3초 이상 늦게 들면 트레이가 기울어 공이 옆 구석에 붙어서, 거칠게 날라도 성공함. 즉 이 과제가 보상하는 기술은 "맞춰 들기"가 아니라 "부드럽게 나르기". (조이콘 스틱은 아날로그라 살살 밀면 됨)
- 목표 가속도 상한(1.0, 0.6 m/s²)도 시험했으나 정지 때 목표를 지나쳐 진동(시간 초과·성공 3~6/10)해서 뺐음. S1·S2 모두 상한 없음.
- 회귀 테스트로 고정: 부드럽게 ≥9/10, 거칠게 ≤2/10.

## D18. S2 높이 = L/R 누른 채 손목 꺾기 (2026-10-20, 사용자 실기 피드백 3회)
- 문제(사용자): "잡은 뒤에 높낮이를 조절해야 공이 안 떨어지게 할 수 있어." 버튼은 "내리기/올리기"만 가능하다.
- 시도 1, 조이콘 위아래 동작(가속도 한 번 적분 + 멈추면 0으로 맞춤): 실기에서 "혼자 달려감". 게임 중 손이 거의 멈추지 않아(회전 중앙값 6~11°/s, 움직이는 중 40~57%) 2초 제한까지 오차가 쌓였다.
- 시도 2, 같은 방식 + L/R 누른 동안만: "아래로만 가거나 확 튐". 누르는 동안 손목이 60~150° 꺾여, 꺾임과 위아래 이동을 구분할 수 없었다.
- **채택**: L/R을 누른 순간의 앞뒤 기울기를 기준으로, 꺾은 각도만큼 속도를 준다. 앞쪽이 내려가면 내려가고, 떼면 그 높이에서 멈춘다. 2.5°부터 움직이고 12°에서 최고(0.15 m/s)다. 중력 방향만 쓰므로 드리프트가 없다. 사용자가 처음부터 하던 동작이기도 하다.
- 남김: `--height motion`(위아래 동작)은 보류 옵션으로 둔다. S1 기본은 버튼 그대로다.
- 왼쪽 조이콘 앞뒤 부호가 반대였다(사용자 보고). 보정 파일에서 부호를 뒤집어 확인했다(PROGRESS 참고).
