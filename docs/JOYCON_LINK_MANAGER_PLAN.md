# 조이콘 연결 관리자(Joy-Con Link Manager) 계획

작성 2026-10-19. 견학 데모(10/21 수, 10/23 금) 전에 "조이콘이 잠든 뒤 다시 붙지 않아 설정에서 제거 → 장치 추가를 반복해야 하는 문제"를 없애는 것이 목표.

## 1. 문제와 현재 상태 (2026-10-19 실측)

| 항목 | 값 |
|---|---|
| 어댑터 | Realtek Bluetooth 5.0 USB (`USB\VID_0BDA&PID_8771`, 드라이버 1.6.1015.3018). Intel 내장 BT는 Error 상태 |
| 등록된 조이콘 | L `XX:XX:XX:XX:XX:XX`, R `YY:YY:YY:YY:YY:YY` — Windows에는 "페어링됨", `IsConnected=False` |
| USB 선택적 절전 | 전원 계획에서 AC/DC 모두 **사용(1)** → USB 동글이 절전에 들어갈 수 있음 |
| 같은 무선에 붙은 장치 | Logitech Pebble(마우스), OP75(키보드), 이어폰 여러 대 → **블루투스 라디오 끄고 켜기는 쓰면 안 됨** |
| 이전 관찰 (PROGRESS) | 해제 후 재연결까지 46~54초(3회), 원인 미확정 |

Windows 설정 화면에는 "연결" 버튼이 없다. 클래식 BT HID 장치는 **조이콘 쪽이 먼저 호스트를 호출(page)** 해야 붙는 구조라서 PC가 잠든 조이콘을 깨울 수 없다. 버튼을 눌러도 안 붙는 경우는 Windows/어댑터가 그 호출을 받아 주지 못한 것이고, 이때 확실히 통하는 복구는 "등록 해제 → SYNC 버튼 → 다시 페어링"뿐이다. 관리자는 이 과정을 **SYNC 버튼 한 번 누르기**로 줄인다.

## 2. 설계 원칙

- **HID를 열지 않는다.** 조이콘 HID는 한 프로세스만 열 수 있다(둘이면 HID read error). 관리자는 Bluetooth 계층(페어링·연결 상태)만 다루고, 리포트 읽기는 기존 `JoyConDevice`가 그대로 맡는다. 그래서 앱과 동시에 띄울 수 있다.
- **우리 조이콘만 자동 처리.** `config/joycon_link.json`에 L/R MAC을 고정하고, 처음 등록할 때만 "이름이 Joy-Con (L)/(R)인 장치"를 받아들인 뒤 MAC을 저장한다.
- **시스템 설정은 바꾸지 않는다.** 전원 설정·드라이버 변경은 사용자가 직접 하거나 승인 후 실행(AGENTS.md 규칙).
- **느린 복구도 화면에 보인다.** 각 손의 상태와 "지금 할 일"(아무 버튼 / SYNC 버튼)을 큰 글씨로 띄운다.

## 3. 구성

```
src/teachabot/btlink/
  winbt.py        WinRT 래퍼: 장치 찾기, 연결 상태 구독, 페어링/해제
  manager.py      손별 상태 기계 + 복구 사다리 (UI 없음, 테스트 가능)
scripts/joycon_manager.py   작은 항상-위 창(tkinter) 또는 --cli 모드
config/joycon_link.json     L/R MAC, 시간 제한 값
```

사용 라이브러리: `winrt-Windows.Devices.Enumeration`, `winrt-Windows.Devices.Bluetooth`, `winrt-Windows.Foundation` (pywinrt, pip 설치. 현재 .venv에 없음).

| 기능 | WinRT API |
|---|---|
| 연결 상태 | `BluetoothDevice.FromBluetoothAddressAsync(mac).ConnectionStatus` + `ConnectionStatusChanged` 이벤트 |
| 페어링 모드 조이콘 찾기 | `DeviceWatcher` (AssociationEndpoint, 클래식 BT 프로토콜, `IsPaired=False`) |
| 페어링 | `DeviceInformation.Pairing.Custom.PairAsync(ConfirmOnly)` + `PairingRequested`에서 `Accept()` |
| 등록 해제 | `DeviceInformation.Pairing.UnpairAsync()` |
| HID 준비 확인 | 기존 `enumerate_joycons()` (hidapi 열거만, 열지 않음) |

## 4. 손별 상태 기계

```
미등록 ──(SYNC 모드 발견 → 자동 페어링)──▶ 연결됨 ──(HID 열거됨)──▶ 준비 완료
                                              ▲                     │
                                              │                (끊김/잠듦)
                                              │                     ▼
                         재등록 ◀──(15초 안에 안 붙음)── 잠듦: "아무 버튼이나 누르세요"
```

복구 사다리 (Phase 0 실측 반영, 2026-10-20):

| 단계 | 동작 | 사람이 할 일 | Phase 0 결과 |
|---|---|---|---|
| L0 예방 | **15분 절전 타이머 경고** (아래 5절) | 경고가 뜨면 아무 버튼 | 버튼 입력만 타이머를 되돌림. 진동·램프 keep-alive는 효과 없음 |
| L1 버튼 깨우기 | 연결 상태 이벤트 대기 | 아무 버튼 | 잠든 뒤 깨우면 대부분 고착(9절). 15초 안에 리포트가 안 오면 L3로 |
| ~~L2 호스트 자극~~ | HID 서비스 끄고 켜기 | — | **제외**: 오히려 더 나빠짐 |
| L3 자동 재등록 | 해제 → SYNC 대기 → 자동 페어링 → HID 확인 | **SYNC 버튼 1번** | 실기 성공(24~56초) |

L3은 고정된 MAC에 한해 자동 실행(결정 2).

## 5. 15분 절전 타이머 대응 (Phase 0에서 바뀐 설계)

조이콘은 **마지막 버튼 입력 뒤 약 15분이 지나면 스스로 잠든다**(9절 실측: 4회 모두 14:58~15:06). 움직임(자이로), 소리 없는 진동 리포트, 플레이어 램프 서브커맨드로는 이 타이머가 되돌려지지 않고, **버튼을 눌러야만** 처음부터 다시 센다. 그리고 잠든 뒤 깨우면 대부분 고착되어 재페어링이 필요하다. 그래서 잠들기 **전에** 사람이 버튼을 누르게 하는 것이 가장 싸다.

- 마지막 버튼 시각은 HID 리포트를 읽는 쪽(앱의 `JoyConInputProvider`)만 안다. 앱이 손별 "마지막 버튼 시각"을 상태 파일(`data/runtime/joycon_status.json`, 1초마다)로 내보내고, 관리자 창이 그것을 읽어 **남은 시간**을 보여 준다.
- 12분이 지나면 관리자 창과 앱 화면에 "L 3분 뒤 잠듦 — 아무 버튼이나 누르세요"를 띄운다. 시연 중에는 학생이 버튼을 계속 누르니 문제없고, 조 교대·쉬는 시간에만 해당된다.
- 앱이 꺼져 있을 때 관리자가 아는 것은 연결 시각뿐이다. 연결 순간(SYNC·버튼)을 마지막 입력으로 보고 15분을 센다.

## 9. Phase 0 결과 (2026-10-19 실측, 진행 중)

도구: `scripts/joycon_link_log.py` (bt = WinRT 연결 상태, hid = HID 목록, rx = 실제 리포트 수신). 로그 `data/logs/link_20261019_215521.jsonl`(HID 안 엶), `link_20261019_221015.jsonl`(`--hold-hid`).

**"고착 상태"의 정체.** 버튼을 누르면 조이콘은 Bluetooth로 붙고(bt=O) HID 목록에도 뜨지만(hid=O), HID를 열면 리포트가 하나도 오지 않는다(`open timed out after 5.0s`, 가끔 `read error`). 호스트가 설정을 끝내 주지 않으니 조이콘은 **11~15초마다 끊고 0.2초 만에 다시 붙기**를 되풀이하다가 약 2~3분 뒤 포기하고 잠든다. 설정 화면에는 계속 "페어링됨"으로만 보인다.

| 관찰 | 결과 |
|---|---|
| ALOHA 앱(t01)이 HID를 잡은 채 L 깨우기 | 앱은 28분 동안 L/R 리포트 0개. L은 2분 40초 동안 11~15초 주기로 끊김·재연결 반복 후 잠듦 |
| 앱 종료 후, HID를 아무도 안 연 채 L/R 깨우기 | 똑같이 11~15초 주기 반복 → 앱 탓이 아님 |

| R(재페어링 안 함)에 L2: HID 서비스 끄고 켜기 | 명령은 성공했지만, 깨우면 bt가 약 1초 만에 끊기고 HID 목록에도 안 뜸 → **더 나빠짐. L2는 사다리에서 제외** |

결론(지금까지): 고착 상태는 재페어링(L3)으로만 풀린다. 고착된 조이콘은 Bluetooth 계층만 봐도 "짧은 주기 끊김·재연결 반복"이라는 신호로 알아볼 수 있다. 다만 정상 조이콘도 HID를 아무도 열지 않으면 같은 반복을 보이는지는 아직 확인하지 못했다.

**방치 테스트 (재페어링 후 HID로 잡고 리포트 받는 중, 손대지 않음).** 둘 다 결국 **조이콘 쪽에서 스스로 잠들었다**.

| 손 | 마지막 손댐 → 끊김 | Windows 이벤트 |
|---|---|---|
| L | 22:23:11 → 22:28:01 (**4분 50초**). 그 전 구간에서는 8분 24초 동안 손대지 않아도 유지됨 | `HidBth` 2 "범위를 벗어났거나 응답 없음" |
| R | 22:22:26 → 22:38:30 (**16분**) | 같음 |

- 끊긴 뒤 스스로 다시 붙지는 않는다(조이콘이 먼저 호출해야 하므로 예상대로).
- 잠드는 시점이 일정하지 않다(4.8분, 16분, 8.4분 넘게 유지된 구간). 그래서 "N분 전에 깨워 두기" 식의 운영은 믿을 수 없다.
- 이벤트 로그 이력(`HidBth` 2, 10/17~19 71건)과 앱 로그로 본 지난 경과: 18:34 잠듦 → 18:59 버튼으로 **정상 재연결**. 19:18:52 L/R 동시에 잠듦 → 20:08~21:33 앱 실행 85분 동안 **한 번도 연결 안 됨(고착)**. 즉 같은 "잠듦 → 버튼 깨우기"가 어떤 때는 되고 어떤 때는 고착된다.

**잠든 뒤 버튼 깨우기 (재페어링 → 방치로 잠듦 → 23:03 버튼).** L/R **둘 다 다시 고착**: bt=O, hid=O인데 HID 열기는 시간 초과·`read error`. 열려 있던 프로세스를 끄고 새 프로세스로 열어도 같았다(남아 있는 핸들 탓이 아님). hidapi로 직접 확인해 보니 출력 쓰기 `write -> -1`, 입력 리포트 0개 → **HID 채널이 양방향 모두 죽어 있다**. 그러니 이 PC + Realtek 동글 조합에서는 **조이콘이 잠들면 다시 페어링해야 하는 경우가 많다**고 보고 설계한다(18:59처럼 정상으로 붙은 경우도 있었음).

→ 운영 전략은 두 가지다. (a) **잠들지 않게 막기**(keep-alive) (b) 잠들었으면 **SYNC 한 번으로 자동 재페어링**.

**Phase 1 재페어링 스크립트 실기 (`scripts/joycon_pair.py LR`, 23:12).** 기존 페어링 해제(ok) → SYNC 대기 → L +51.7s, R +53.8s 페어링 ok → HID 준비 +54.4s / +56.4s → 바로 리포트 수신. 설정 화면은 열지 않았다. 고친 버그 세 가지:
- `DeviceWatcher`는 Updated·Removed 핸들러가 없으면 Added를 아예 발생시키지 않는다.
- AEP 속성값이 감싼 객체(`_winrt.Object`)로 와서 MAC 비교가 항상 실패했다 → 기기 id 끝부분의 주소를 쓰도록 변경.
- 해제된 조이콘은 이름이 처음엔 "Bluetooth 70:2c:…"일 수 있다 → 저장된 MAC으로 매칭.
- 남은 문제: Windows가 SYNC 모드가 아닌 조이콘도 목록에 보여 주므로, SYNC 전에 시도한 페어링은 `AUTHENTICATION_TIMEOUT`이 나기까지 **약 22초를 잡아먹는다**. 그 사이 SYNC를 눌러도 다음 시도까지 기다려야 한다 → Phase 2에서 L/R 병렬 시도, 짧은 재시도로 개선.

**keep-alive A/B (23:14~, L만 1초마다 소리 없는 진동 리포트 0x10, 전송 실패 0회).** L 23:28:58, R 23:29:00에 끊김 → **진동 리포트 keep-alive는 효과 없음**.

**잠드는 시점은 "약 15분"으로 일정했다.** 앞의 "4.8분/16분"은 마지막 손댐 기준이라 틀린 해석이었다. HID 연결 시점부터 재면:

| 회차 | 연결(HID 열림) | 끊김 | 경과 |
|---|---|---|---|
| L 1차 | 22:12:55 | 22:28:01 | 15:06 |
| R 1차 | 22:23:31 | 22:38:30 | 14:59 |
| L 2차 (keep-alive) | 23:14:00 | 23:28:58 | 14:58 |
| R 2차 | 23:14:00 | 23:29:00 | 15:00 |
| (앱 로그) L/R | 18:59:37 연결, 앱 사용 ~19:04 | 19:18:52 둘 다 | 마지막 사용 기준 약 15분 |
